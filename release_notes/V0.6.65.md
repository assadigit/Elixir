# V0.6.65 — "it doesn't open at all": the first real-machine install report, answered — startup can no longer die silently (a launcher guard that catches pre-window crashes into `startup.log` + `startup_crash.log` + a Qt-free native error box), the single-instance FOCUS protocol is actually wired now (it was never connected: a second double-click exited silently while the first window never came forward — plus a zombie-takeover path so a hung first instance can't lock you out forever), an instant "Elixir is starting…" splash so a slow first launch (cold disk, antivirus scanning every DLL) no longer looks like a dead app, and a `qwindows.dll` precheck that turns the classic antivirus-stripped-bundle failure into an actionable message

## The report this ships

> "I've installed the app, it got installed on my windows, but it doesnt
> open at all."

First-ever install of `Elixir-Setup-0.6.64.exe` on a real Windows machine
(the release asset's 1 download). Both CI builds of that release were
green — including a real window-appears launch test and a silent
install → launch → uninstall loop on a clean Windows runner — so the
failure was machine-specific. The problem: **every pre-window failure in
a windowed (no-console) build is invisible.** No window, no console, no
dialog, no file the user knows about. The app had crash machinery
(faulthandler, an excepthook with a crash-report zip, a stderr sink) —
but all of it arms *after* the risky early imports, none of it can show
anything *before* Qt exists, and one of the most plausible failure modes
made every later double-click exit on purpose.

## What was actually wrong (found by reading the startup path end-to-end)

1. **The single-instance FOCUS protocol was never wired.** Since V18.1
   the second launch sent `FOCUS` to the first instance and exited —
   but the first instance never connected the server's
   `newConnection` handler: **nobody read the pipe, and the existing
   window never came forward.** On a machine where the first launch was
   still starting up (or hung without a window), every subsequent
   double-click did *nothing at all*, by design. That is the reported
   symptom, exactly.
2. **Pre-window crashes were unreportable.** The very first project
   import (`utils.settings`), the torch probe, the dependency checks,
   and the first steps of `ui_qt.app.run` — including `QApplication`
   construction itself — all ran before any excepthook existed, and the
   app's own excepthook showed a dialog only when a QApplication already
   existed. In a windowed build: silent death.
3. **No liveness feedback.** A slow first launch (cold disk, antivirus
   scanning each of the ~2,000 bundled DLLs as it loads) looked
   identical to a dead one — and every extra double-click made it worse
   via bug 1.
4. **The antivirus signature case.** "Nothing happens, no logs at all"
   is also what an unsigned PyInstaller bundle looks like after
   antivirus strips files from it. The one such failure Python can see
   in advance — a missing Qt `qwindows.dll`, which kills Qt with an
   uncatchable `qFatal` abort — deserved a pre-check and a plain-words
   message instead of a dead click.

## The fixes

- **`core/system/launcher_guard.py` (new, stdlib-only, never raises):**
  armed as the FIRST statement of `main.py`, before every other project
  import. It opens `%LOCALAPPDATA%\Elixir\startup.log` (a timestamped
  timeline of every startup step — see an example below), installs a
  `sys.excepthook` that writes the full traceback to
  `startup_crash.log` (plus a copy next to `Elixir.exe`), and shows a
  **Qt-free native Windows error box** (`MessageBoxTimeoutW` — works
  before QApplication, needs no plugins, auto-closes after 90 s so
  unattended sessions can't hang on it) with the error and the report
  path in plain words. `main.py`'s own excepthook also gained the
  missing pre-QApplication branch.
- **The lock protocol, actually implemented:** the primary now answers
  `FOCUS` by raising its window and replying `OK`; a second launch that
  gets the ACK exits quietly (window comes forward); a second launch
  that gets **no ACK within 2.5 s** concludes the primary is hung and
  **takes the lock over** instead of exiting forever.
- **`_StartupSplash`:** a tiny always-on-top "◆ Elixir is starting…"
  label the moment the lock is acquired, closed when the main window
  appears (built inside a try/except — it can never block startup).
- **`precheck_qt_platform_plugin`:** before the Qt import, verifies the
  Windows platform plugin exists in the bundle; if it's gone, shows the
  antivirus message ("check Protection history, restore, add an
  exclusion, reinstall") instead of letting Qt die silently.

## Verified here (offscreen, end-to-end)

- **Launch:** first instance starts, splash → window up, stays alive;
  `startup.log` records the whole timeline:
  `guard armed → selftest dispatch → dependency + numpy ABI checks →
  bootstrap (+1.6 s) → Qt platform plugin precheck (+1.5 s) → Qt UI
  launch`.
- **Second launch while the first runs:** sends `FOCUS`, receives the
  ACK, **exits 0 in 3.7 s** (its own Python startup; the ACK itself was
  instant — no takeover warning fired). The first instance keeps
  running.
- Full suite: **8,613 passed / 16 failed / 25 skipped in 4:29** — the
  **same 16 documented pre-existing failures** as V0.6.64 (same test
  IDs), +29 collected (the new guard/protocol/splash pins, all green).
  Zero regressions; every suspicious failure was verified identical on
  the stashed pre-change HEAD.
- Source selftest: **377/377 modules** (the new module joins the walk),
  0 failures, exit 0. ruff repo-wide: 1 check finding — the OFF-LIMITS
  vibevoice-compat B023, left by instruction, unchanged.

## If it still doesn't open (the troubleshooting path, in plain words)

1. Open File Explorer, paste `%LOCALAPPDATA%\Elixir` in the address bar,
   press Enter. The files there (`startup.log`, `startup_crash.log`,
   `faulthandler.log`, `console.log`) tell the whole story — send them
   to the developer.
2. If that folder is empty/missing: the app never even started — check
   **Windows Security → Virus & threat protection → Protection
   history** for quarantined Elixir files; restore them, add the
   install folder to allowed threats, and try again.
3. Still nothing? Right-click the Start-menu "Elixir" → Open file
   location → double-click `Elixir.exe` directly and watch for the
   new error box — it names the problem and where the report was saved.

## Risks and unverified parts (honest list)

- **The zombie-takeover tradeoff:** a *healthy* primary whose event
  loop is busy > 2.5 s (e.g. mid-conversion) will be taken over — two
  windows may briefly coexist. That is strictly better than the old
  behavior (silent exit; "the app stopped opening"), but it is a real
  behavior change, logged loudly.
- The native error box is Windows-only (stderr print elsewhere); the
  90 s auto-close uses the `MessageBoxTimeoutW` export with a plain
  `MessageBoxW` fallback.
- The real fix for antivirus stripping is **code signing** — a paid
  certificate decision that belongs to the owner, not taken here.
- All rendering/protocol verification here is Linux offscreen; the
  Windows-only paths (native box, `qwindows.dll` precheck) are pinned
  by unit tests with faked frozen environments, not on a real Windows
  box — the next installer CI run exercises the real thing end-to-end.
