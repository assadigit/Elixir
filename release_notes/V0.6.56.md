# V0.6.56 — the Transcribe Service internal log container: the 10-minute "frozen or progressing?" wait ended — the whisper CLI now STREAMS line-by-line into a live log, a 15s heartbeat proves the app is alive while the engine is silent, and one review BLOCKER (an `isRunning()` API crash that would have fired 15 seconds into every run) was caught and fixed pre-release — 30 new pins / 405 P affected sweep / 0 regressions

## The user report

> "add an internal log container like other tools of this app has,
> because i waited 10 minute to no avail and i wasn't sure it's frozen
> or progressing"

The report named the SYMPTOM (no visibility), and the investigation
found the root cause was worse than a missing widget: **the engine was
structurally silent.**

## Root cause 1 — the engine: `subprocess.run(capture_output=True)`

`transcribe_with_cpp` ran the whisper CLI with ALL output trapped in
memory until the process exited. Between `progress(20)` ("Running
transcribe.cpp…") and `progress(100)` (post-parse) the pipeline
emitted **nothing at all** — for a 15-minute video that is many
minutes of total silence. No log container could have shown progress
because there was no progress to show.

**The fix — `_stream_cli_output`.** The CLI now runs via `Popen` and
two daemon reader threads (one per stream, so both work on Windows
where `select()` cannot multiplex pipes) pump stdout/stderr
line-by-line while the run is in flight:

- **every CLI line is echoed to the live log** prefixed
  `  [whisper] …` — the transcript visibly builds while whisper
  works (the actual "progressing" proof the operator wanted);
- `### 42%`-shaped progress bars and `progress = 42%` callbacks map
  onto the dialog's progress bar (the 20..90 slice; integer-percent
  dedup so spinner spam doesn't flood). A transcript line that merely
  CONTAINS a percent ("I am 100% sure") is echoed but never mapped —
  the review caught the naive regex moving the bar backward;
- `\r` spinner frames collapse to the latest frame;
- the accumulated text stays **byte-faithful** to what
  `capture_output=True` produced — the P6 parser's input is
  unchanged (pinned), so parsing behavior is identical;
- the timeout is now a MONOTONIC deadline enforced by a 0.5 s poll
  (kills the CLI on expiry — the legacy timeout error string
  verbatim), and if the streamer itself raises post-Popen the CLI is
  killed instead of leaking (holding the GPU with a filling pipe
  nobody drains);
- the ffmpeg 16 kHz conversion moved to `_convert_to_wav16k`
  (verbatim error strings) — which also fixed a quiet bug: the old
  code handed the `NamedTemporaryFile` OBJECT to `_cleanup_temp`,
  whose `Path()` raised into the best-effort except, so temp WAVs
  were **never actually deleted**; the string path deletes them now.

## Root cause 2 — the dialog: the log container existed but was hidden

`BaseServiceDialog` already ships the live-log toggle + panel every
other tool uses; this dialog hid the toggle as "dead" (its
`_on_progress` override dropped every message on the floor — only the
one-line status label survived). V0.6.56 wires it all up:

- the toggle is visible again and the log **auto-opens + clears on
  every run** (the packets-tool precedent: never make the operator
  FIND the log mid-run), with a run header — file (+size), engine,
  model, requested outputs — so the configuration is on record;
- **every pipeline message lands in the log** with a timestamp
  (ffmpeg, whisper lines, LLM connection resolution, chunk growth,
  savings, the structured P5 errors). The streaming "📝 LLM is
  writing" lines are sampled every 10th in the LOG (the status label
  still updates on every chunk — P4's contract) so a long generation
  doesn't bury the real events;
- **the 15-second heartbeat** (a QTimer, started before the worker
  spawns, stopped on every completion path): while a run is alive the
  log gains `⏱ still working — 03:15 elapsed, last pipeline update 45s
  ago: <last message>` — the elapsed-vs-gap pair is precisely the
  frozen/progressing discriminator: pipeline lines landing between
  heartbeats = progressing; heartbeats only with a growing gap =
  the engine is silent (model load / an LLM on CPU), and past 2
  minutes of silence the line appends the triage hint (model-load /
  CPU-fallback can take minutes; 🔌 Test checks the LLM; kill + retry
  if it never advances);
- the 🔌 Test LLM connection button's start + verdict lines also land
  in the log (the message box disappears; the record stays for the
  paste-back).

The new `core/transcribe/pipeline_log.py` (Qt-free, stdlib-only leaf)
formats the heartbeat + run header and is unit-tested directly — no
PySide6 needed.

## The review BLOCKER (caught pre-release, again)

The fresh-eyes subagent (the V0.6.55 pattern — it pays for itself)
found the heartbeat calling `worker.isRunning()`. `SimpleWorker` is a
`BaseWorker` = **QObject**, whose liveness API is `is_running()`;
`isRunning()` is QThread-only. Fifteen seconds into every run the
heartbeat would have raised `AttributeError` → the global excepthook
(modal crash dialog) → **a new crash dialog + crash zip every 15 s
for the whole run**. Invisible in this no-Qt sandbox and initially
pinned in by the very test file meant to prevent it. Fixed via the
house `_worker_is_running` helper (shared.py — it normalizes both
worker shapes), with the pin now asserting the helper AND banning
`isRunning()` from the method forever.

All four SHOULD-FIX items landed too: the percent anchoring (above),
the monotonic deadline, the callback-exception isolation (a raising
callback can truncate the echo, never the accumulated parse input),
and the post-Popen kill.

## Behavior notes

- The whisper run is now visibly chatty in the log; the log panel is
  180 px tall, auto-scrolls, and is user-toggleable as before.
- Progress-bar percent moves on progress-bar-shaped lines only;
  transcript text with "%" no longer moves it.
- The heartbeat is diagnostic-only — it never touches the pinned
  plain-text status-label contract (e2e drive tests unchanged).
- The temp-WAV cleanup fix means `%TEMP%\transcribe_cpp_*.wav` files
  from failed runs are actually deleted now.

## Rig-only boundary (the honest limit, unchanged in kind)

Visual layout of the log panel/heartbeat lines, and the real CLI's
actual line formats (the raw_output.txt dump on the rig shows exactly
what the echo will look like). If the rig's transcribe-cli emits
progress in a shape the new anchors don't recognize, the lines are
still ECHOED (just not percent-mapped) — paste the raw_output.txt and
the anchors get one more alternative.
