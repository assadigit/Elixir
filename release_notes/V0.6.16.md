## The diagnosis (reproduced byte-for-byte, then fixed, against the real stack)

The traceback's `auto_factory.py` line numbers (register at 427, the
ValueError at 672) fingerprint the rig's transformers as a **v5.13–v5.17
build**. Those versions ship VibeVoice **natively** (`models/vibevoice*`),
and the auto-generated registry (`models/auto/auto_mappings.py`, line 684
in 5.17.0) pre-registers the config-class **name**
`VibeVoiceAcousticTokenizerConfig`. The from-source VibeVoice checkout
(`C:\VibeVoice`) re-registers its OWN class with that same name at import
time (`modular/modular_vibevoice_tokenizer.py:1200` — bare
`AutoModel.register(...)`, no `exist_ok`), and transformers'
`_LazyAutoMapping.register` checks duplicates **by class name** — the very
first import dies, and every podcast stops at line 1.

And one import later, the SAME transformers v5 breaks the package a
SECOND time: the per-model `*_fast` tokenizer submodules were removed
(`transformers.models.qwen2.tokenization_qwen2_fast` no longer exists;
`Qwen2TokenizerFast` now lives in `transformers.models.qwen2` directly),
while `modular_vibevoice_text_tokenizer.py` still imports the legacy
path — a `ModuleNotFoundError` waiting right behind the first fix.

Both were verified against the real dependencies, not by reading alone:
a lab venv (torch 2.14 CPU + transformers 5.17.0 + the current
microsoft/VibeVoice checkout) reproduced the operator's traceback
**byte-for-byte** unpatched, then imported cleanly with the fix —
and the fix was re-verified across the whole affected range
(transformers 5.13.0, 5.17.0, 5.18.0: fixed; 4.57.1: byte-identical
no-op, the no-regression proof).

## The fixes (2 runtime files, +19 tests)

- **`core/tts/_vibevoice_subprocess.py`** — a transformers-v5
  compatibility layer (`_install_transformers_compat()`, installed
  before the first vibevoice import), in two parts:
  1. `_tolerate_native_vibevoice_register()` — the duplicate
     registration is made harmless: the register call is retried with
     `exist_ok=True` (the from-source class wins — the exact end-state
     of a transformers WITHOUT native vibevoice) and a NOTE names what
     happened. The mapping entry is cosmetic for us (the streaming
     inference path instantiates its classes directly), so this is safe.
     Primary patch: the shared `_LazyAutoMapping.register` (the choke
     point every `Auto*.register` flows through — covers the package's
     `AutoModel` AND `AutoModelForCausalLM` sites). Fallback: the
     documented `AutoModel.register` / `AutoModelForCausalLM.register`
     classmethods (if the private path ever moves). Unpatchable → a
     WARNING naming the `transformers<5.13` pin, never a crash.
  2. `_alias_legacy_tokenizer_modules()` — the removed
     `tokenization_qwen2_fast` submodule is pre-registered in
     `sys.modules` as a one-attribute alias built from the package's own
     class; on transformers < 5 the real module exists and nothing is
     aliased at all.
  The subprocess now also logs its transformers version at load (the
  line the next diagnosis will want first). The V11.57 no-restart and
  V18.20.4.4 kill-before-raise contracts are byte-identical (pinned).
- **`core/tts/vibevoice_engine.py`** — defense in depth: if the
  subprocess-side tolerance could not be installed (a future
  transformers layout change), the load-error raise now explains the
  collision and names the two outs (update Elixir / pin
  `transformers<5.13`).
