## The diagnosis (reproduced byte-for-byte, then fixed and proven end-to-end, against the real stack — model included)

transformers v5 builds **every** `from_pretrained` model on the **meta
device** — unconditionally, because `low_cpu_mem_usage` was *removed* in
v5 ("Not used anymore -- remove them from the kwargs",
`modeling_utils.py:4240` in the rig's 5.14.1). Under
`with torch.device("meta")`, every device-unspecified tensor **factory**
call (`torch.tensor`, `torch.linspace`, `torch.empty`, …) produces a
meta tensor — a shape without data — while `torch.from_numpy` is NOT
redirected. transformers' own `meta_device_safe_creation_ops` patches
only `torch.linspace` against this (identical in 5.14.1 and 5.17.0;
`torch.arange` deliberately not patched, `torch.tensor` not patched at
all). VibeVoice-Realtime's config uses `ddpm_beta_schedule: "cosine"`
(verified in the real checkpoint's config.json), so the scheduler's
betas come from `betas_for_alpha_bar(...)` → `torch.tensor(...)` → a
**meta** tensor, and dpm_solver.py:295's `.to("cpu")` dies — while the
scheduler's `timesteps` (`from_numpy`) stayed real, exactly matching the
operator's traceback.

This time the lab went all the way: the real
`microsoft/VibeVoice-Realtime-0.5B` checkpoint (2 GB) was downloaded and
the operator's traceback reproduced **byte-for-byte** unpatched
(transformers 5.14.1 — the rig's exact build — + torch + microsoft/
VibeVoice @ main). Fixing the scheduler exposed **three more v5
breakages in the same chain**, each surfaced by the live end-to-end
proof and fixed before shipping: (2) `init_weights()` calls
`tie_weights(recompute_mapping=False)` — kwargs the from-source
no-argument override (line 204) rejects; (3) the custom `generate()`
calls `_prepare_generation_config(config, True, speech_*=...)` — v4's
second positional + speech ids against v5's
`(generation_config, **kwargs)` signature; (4) the official voice
presets pickle transformers-4.5x `DynamicCache` internals
(`key_cache`/`value_cache` lists — verified inside the real
`en-Carter_man.pt`), which v5's rearchitected cache rejects on the
first forward ("`get_seq_length` can only be called on Attention
layers…" — VibeVoice's own MockCacheLayer bridge, written for 4.57,
fails v5.14's strict isinstance check). The final proof: the real
checkpoint + the real preset **generated a real 4.7 s WAV** through the
production load path on BOTH transformers 5.14.1 and 5.17.0 (879
params, zero meta leaks, real scheduler sigmas).

## The fixes (2 runtime files, +37 tests)

- **`core/tts/_vibevoice_subprocess.py`** — four additions, all
  installed after the vibevoice import and before `from_pretrained`
  (one line too late is a dead load):
  1. `_guard_scheduler_meta_init()` — wraps
     `DPMSolverMultistepScheduler.__init__`: when a meta context is
     active (probed via `torch.empty(0).is_meta`) it re-enters
     `with torch.device("cpu")` around the original init. torch keeps a
     SINGLE DeviceContext at the bottom of the function-mode stack, so
     the nested CPU context REPLACES the meta one for the duration —
     every factory call then produces a real CPU tensor (proven live
     for BOTH mechanisms: the v5 device context manager AND the
     accelerate-style `torch.utils._device.DeviceContext` that
     transformers v4 + device_map uses). The scheduler holds no
     checkpoint state (zero scheduler keys in model.safetensors —
     verified), so it must be built real at init time; parameters and
     buffers stay on the meta path and are materialized by
     from_pretrained as usual (the nan scaling buffers ARE in the
     checkpoint — verified). Fast path: no meta context → the original
     init runs untouched. Idempotent, never raises.
  2. `_tolerate_v5_tie_weights_signature()` — the model class's own
     `tie_weights` override is wrapped to accept-and-drop v5's
     `missing_keys`/`recompute_mapping` kwargs (both verified unused by
     the from-source logic; v4 calls it bare and passes through). Any
     OTHER unexpected kwarg still propagates — a future drift must
     surface loudly, not be swallowed.
  3. `_tolerate_v5_prepare_generation_config()` — the inherited mixin
     method is shadowed on the model class with a wrapper that drops
     v4's second positional (`use_model_defaults` — consulted only
     when the config is None, which VibeVoice never does) and the three
     speech ids (re-set by the caller on the very next lines); verified
     against the 4.51.3 source that the drops are semantically
     identical on v4 and v5 alike.
  4. `_modernize_legacy_preset_cache()` (+ `_legacy_cache_needs_rebuild`
     / `_rebuild_legacy_preset_cache` / `_preset_cache_outputs`
     helpers) — each 4.5x cache inside a voice preset is rebuilt
     layer-by-layer through the INSTALLED version's
     `DynamicCache.update()` (real CacheLayerMixin layers, the tensors
     themselves untouched); VibeVoice's own bridge then no-ops on the
     result. A preset already in the new format is left alone (re-saved
     v5 presets keep working). One NOTE per process (the preset
     reloads for every line — 113 lines × 4 caches must not flood the
     log). Best-effort, never raises.
  The load call also passes the version-gated dtype kwarg
  (`dtype` on transformers ≥ 5, `torch_dtype` on v4 — the rig's log
  showed the deprecation warning on every load). The V11.57 no-restart
  and V18.20.4.4 kill-before-raise contracts are byte-identical
  (pinned).
- **`core/tts/vibevoice_engine.py`** — defense in depth: a load error
  carrying "meta tensor" now explains the meta-device init and names
  the two outs (update Elixir / pin `transformers<5`) — it fires only
  if the subprocess-side guard itself could not be installed.
