# V0.6.66 — the second "doesn't open" report, answered: the Windows installer no longer rides unpinned package drift (it shipped the exact PySide6 6.12.0 / mammoth 1.13.0 / markitdown 0.1.9 combination documented to segfault), refuses Windows < 10 instead of installing a never-launching app, force-replaces a hung old Elixir.exe during upgrades, and gains a one-double-click "Elixir - Collect Diagnostics" Start-menu tool so the next field report arrives with evidence instead of silence

## The report this ships

> "I've installed the latest version on my windows, it didn't open,
> findout whats the problem. it goes silently fail. it shows app and
> everything in the search and start menu but doesnt open."

Second real-machine report, one day and one release after V0.6.65's
launcher guard made every Python-level startup failure visible
(`startup.log` timeline + native error box + splash). **Silent again**
means the death happens at a level the guard cannot reach — or the
machine never got the fixed build. Both CI builds of V0.6.65 were green
including the packed + installed window-appears launch tests on a clean
Windows runner, so the bundle demonstrably *can* start. The difference
between "green in CI" and "silent on the user's machine" pointed at the
build inputs themselves.

## What was actually wrong (found by forensics on the released artifacts)

The Windows workflow installed **unpinned** `requirements.txt` (a stale
comment claimed the Linux lock was unsolvable on Windows because of a
magika/onnxruntime conflict — today's resolution disproves that note).
The CI job log for `Elixir-Setup-0.6.65.exe` shows what pip resolved on
the morning of 2026-10-24:

- **PySide6 6.12.0** — the newest Qt, not the verified 6.11.2
- **mammoth 1.13.0**, **markitdown 0.1.9** — the doc-chain drift set

That is **the exact trio that deterministically segfaulted the test
suite on Linux** in the documented lock-alignment incident (the incident
that created `requirements.lock`'s rule). The lesson was applied to
Linux — both the sandbox recipe and the Linux CI job install the pinned
closure — but the Windows build kept floating. A clean, freshly-imaged
CI runner tolerated the stack; the first real consumer machine
(hardware drivers, antivirus, a different update state) did not. Same
hazard, one platform over.

Two more silent-failure traps surfaced in the same read-through of the
installer template:

1. **Windows 7 / 8.1 installs.** The installer had no `MinVersion`, but
   Python 3.12 requires Windows 10+ — on anything older the installer
   completes happily, the Start menu shows Elixir, and the app dies in
   the bootloader at every launch: **silently, forever, by design of the
   OS**. If the reporting machine is Win 7/8.1, this alone is the whole
   story.
2. **The in-use-file trap.** A hung `Elixir.exe` from a previous
   install (e.g. the V0.6.64 zombie the first report described) blocks
   the upgrade from replacing the exe; the Start-menu shortcut keeps
   launching the **old** build until the next reboot.

## The fixes

- **`requirements.windows.lock` (new):** the Windows build's pinned
  closure — the full 2026-10-24 runner resolution (which passed the
  packed selftest + launch tests) with the three dangerous packages
  downgraded to the globally verified versions (PySide6 family
  **6.11.2**, mammoth **1.11.0**, markitdown **0.1.7** — the same pins
  `requirements.lock` proves on Linux) plus the three transitive pins
  that follow the markitdown downgrade (magika **0.6.3**, onnxruntime
  **1.20.1** — magika's win32 marker caps it there, the true origin of
  the old "unsolvable on Windows" note —, youtube-transcript-api
  **1.0.3**; the first CI attempt without them hit
  `ResolutionImpossible`). Verified solvable for win_amd64 / Python
  3.12 by a cross-platform `pip --dry-run` before the retag. The header documents the
  regeneration rule so the set stays current *deliberately*, never by
  drift. `windows-installer.yml` now installs this lock and pins
  `pyinstaller==6.22.3` (the bootloader builder is as much a dependency
  as any package).
- **`MinVersion=10.0`** in the Inno Setup template: on Windows 7/8.1
  the installer now refuses with a clear message instead of installing
  an app that can never launch.
- **`CloseApplications=force`:** upgrades force-close a hung previous
  `Elixir.exe` (Restart Manager) so the new exe actually replaces the
  old one — no more stale-shortcut-after-upgrade.
- **`packaging/collect_diagnostics.cmd` + Start-menu shortcut
  "Elixir - Collect Diagnostics":** one double-click gathers everything
  a support person needs into `Desktop\Elixir-diagnostics\` — the app's
  own `startup.log` / `startup_crash.log` / `faulthandler.log`
  timeline, the Windows version/build, running Elixir processes,
  Defender threat-detection history, the install-folder integrity
  (Elixir.exe, `_internal`, `qwindows.dll`, `python312.dll`, VC runtime
  DLLs), and free disk space — then opens the folder. Pure ASCII, CRLF,
  best-effort in every step: a failing step is skipped, nothing is ever
  changed on the user's machine.

## Verified here

- **11 new guard tests** (`tests/test_v0666_windows_lock.py`): the lock
  exists, pins the verified trio, forbids the documented-bad versions by
  name, contains only exact pins; the workflow installs the lock (not
  `requirements.txt`) and pins pyinstaller; the ISS template sets
  `MinVersion=10.0` + `CloseApplications=force` + ships and shortcuts
  the diagnostics collector; the collector is ASCII/CRLF and covers the
  log copy, Defender checks, and `qwindows.dll` presence.
- The Windows-only parts (installer behavior, .cmd execution) are
  exercised for real by the installer CI run this release triggers:
  silent install → packed selftest → **launch test (window must
  appear)** → silent uninstall, now built from the pinned lock.

## If it still doesn't open (the plain-words path, in order)

1. **Check your Windows version:** press `Win+R`, type `winver`, Enter.
   If it says Windows 7 or 8/8.1 — that is the answer; Elixir needs
   Windows 10 or newer (the new installer says so instead of
   installing).
2. **Check antivirus interference:** Windows Security → Virus & threat
   protection → **Protection history**. Any Elixir entry = restore the
   file, allow the threat, add the install folder
   (`%LOCALAPPDATA%\Programs\Elixir`) to exclusions, and reinstall.
3. **Kill any zombie:** Ctrl+Shift+Esc → Details tab → end every
   `Elixir.exe` you see → launch again.
4. **Send the evidence:** Start menu → **"Elixir - Collect Diagnostics"**
   → attach the `Elixir-diagnostics` folder it drops on your Desktop.

## Risks and unverified parts (honest list)

- The trio downgrade is verified on Linux (the whole suite runs on
  6.11.2 / 1.11.0 / 0.1.7) and will be proven on Windows by this
  release's own installer run — but the *full* 861 MB bundle on a real
  consumer machine can only be proven by the user's next install.
- The rest of the pinned set (numpy 1.26.4, onnxruntime 1.31.0,
  pandas 3.0.6, …) is pinned to **what the green V0.6.65 CI build
  actually resolved** — passed the runner's selftest + launch gates,
  but not separately audited on real hardware.
- `collect_diagnostics.cmd` is deliberately simplistic (pure batch +
  inline PowerShell, no parameters, no config). Untested on a real
  Windows box before this release; every step is wrapped so the worst
  case is an empty output file, never a damaged machine.
- If the user's machine fails for a reason outside all of the above
  (e.g. a third-party antivirus stripping DLLs), the pins alone will
  not fix it — but the diagnostics folder will finally show it.

## How to undo

`git revert <release commit>` — the packaging changes, the lock, the
collector, and the tests are one commit on `main` (plus the tag
`V0.6.66`).
