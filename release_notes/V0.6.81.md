# V0.6.81 — the compiled-Windows "not enough space" fix: the measured reflow · the screen-aware reference default (fresh installs open at the 1536×1024 composition) · the no-clip window floor · the reference's exact two-line headline · the QSS capsule that renders on Windows

> **The field report behind this release:** *"Same thing happened
> again. not enough space in the compiled app in windows. but your
> preview shows correctly."* — the second recurrence of the same
> symptom. The root cause was never the Windows build: the reflow
> decisions were made against numbers that were only true on the dev
> box.

## The measured reflow (the core fix)

The Quick Tools column count was chosen by fixed pixel thresholds
(`_GRID_3_MIN_W = 820`, `_GRID_2_MIN_W = 520`) tuned on the dev box's
Inter. On Windows — Segoe UI runs ~10% wider whenever the bundled Inter
fails to register — a ~530 px content run picked 2 columns that needed
~620 px: the home view's minimum width exceeded the scroll viewport and
the right column + the "View all tools" action clipped out of sight.
The dev-side preview, rendering the same geometry with narrower glyphs,
looked fine. That is the entire preview-vs-compiled discrepancy.

The count is now decided by **measurement**: candidates are tried
3 → 2 → 1, and a count is only kept when the page's own
`layout().minimumSize()` — every card title, the heading row and the
hero at the real metrics of the running font stack — fits the width the
scroll viewport is actually offering. Measurement cannot drift from any
font stack.

Two Qt traps made the measurement necessary:

1. **The clamp deadlock.** A widget's implied minimum is its layout's
   `minimumSizeHint`, so while the grid was 3-wide (a ~980 px page
   minimum) the `QScrollArea` could never resize the HomeView below
   ~980 px — the resize events reported the CLAMPED width, the reflow
   never saw the narrow viewport, and the column count deadlocked at a
   size that clipped. The HomeView now sets an explicit 1×1 minimum
   (an explicit minimum overrides the hint), so the true viewport width
   always reaches the reflow.
2. **The one-cycle-stale page minimum.** Re-parenting layout items
   does not refresh the page-level `minimumSize()` until a posted
   LayoutRequest is processed — an in-event check would compare
   against the PREVIOUS column count's minimum. `_lay_grid_columns`
   finishes with `self.layout().activate()`, which recomputes
   synchronously.

**Verification** — a resize sweep across the real containment
(QScrollArea, exactly as the app wraps the view) on two font stacks:

| Window | Inter run | Inter cols | Wide-font run | Wide-font cols |
|---|---|---|---|---|
| 760 (min) | 439 | 1 | 439 | 1 |
| 892 (the reporter's) | 571 | 1 | 571 | 1 |
| 1000 | 679 | 2 | 679 | 1 |
| 1200 | 879 | 2 | 879 | 2 |
| 1340 | 1027 | 3 | 1027 | 3 |
| 1536 (reference) | 1223 | **3** | 1223 | **3** |

**Zero overflow failures from the 760 px minimum window to 1600 px on
either stack.** The user's ~900 px window now degrades cleanly to 1
column instead of clipping; the reference window shows the full 3×3
grid on BOTH stacks.

## The screen-aware reference default

A fresh install used to open at 760×540 — a window that can never
compose the dashboard (the reference composition needs a ~1340 px
window on Inter, ~1380 on wider stacks). Fresh installs — and the
V0.6.68–80 "never-resized" 760×540 fingerprint saves, stamped or not —
now open at the approved reference composition: **1536×1024 scaled to
~92% of the primary screen's work area**, never below 760×540. On a
1920×1080 display at 125% scaling (the reporter's class of machine) the
window opens at exactly the reference width with the full dashboard
composed. Deliberate hand-resizes keep their meaning; every pinned
geometry constant is untouched (the V0.6.67/68 test suite passes
unchanged).

The window minimum rises 560×400 → **760×440**: the 560 floor predates
the dashboard and sat permanently below ONE card column's minimum, so
the smallest legal window could only ever render clipped.

## The reference's exact two-line headline

The correction spec pins the hero lines verbatim:

```
Turn documents into
clear, structured knowledge.
```

Greedy wrapping can never produce them: at 41 px Inter SemiBold the
second line (≈567 px) is WIDER than the first line plus the next word
(≈529 px), so any wrap that fits line 2 inside the ~545 px column
necessarily drags "clear," onto line 1 — the V0.6.80 render wrapped
exactly that way. The break is now a hard newline at the measured
**39 px** display size (the reference's effective headline size), with
the wrap cap kept as the narrow-width guard. Verified in the capture:
the headline renders as exactly the two reference lines.

## The hero grows instead of clipping

The hero's height was FIXED in V0.6.80 (to stop the wordWrap sizeHint
leak). On a taller font stack that fixed height cut the CTA / the
heading's last line — the height is now a MINIMUM at the reference
proportion: the height-for-width floor grows the hero exactly as much
as the real text needs and no more. At the reference viewport the
layout minimum stays under 340 px, so the V0.6.80 no-scrollbar
guarantee holds; on a wider stack the hero stretches a few pixels
instead of eating its own content.

## The capsule that renders on Windows

The field screenshots show every `border: none` + `border-radius`
QPushButton painting as a **square** on Windows (the hero CTA, the
dialog Primary) while every bordered control (cards, pills) rounded
correctly: Qt's QSS engine only clips a button's background to the
radius when a border exists. Both rules now carry a 1 px self-coloured
border (an invisible seam), with hover/pressed/disabled border-colours
following their fills.

## Bundle-robust Inter registration

`load_inter` resolves `assets/fonts` through `app_paths.bundle_dir()`
(the house pattern for every bundled resource) instead of
`Path(__file__).parent.parent` — if the registration silently fails in
a frozen layout, the QSS stack falls back to the wider Segoe UI and
every fixed threshold in the app under-measures. The measured reflow
removes the dependency on that assumption; this makes the font path
itself robust too.
