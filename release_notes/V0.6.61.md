## The LIVE discovery (the headline)

Probing Hugging Face's real xet CDN with `Range: bytes=1000-` plus a
BOGUS `If-Range` etag: **the CDN answers 206, not 200** — it serves
the partial body without validating If-Range at all. Consequence: the
V0.6.60 ETag/If-Range "republished remote restarts instead of mixing"
defense is SERVER-DEPENDENT and does not bind the CDN the rig actually
downloads from. A stale `.part` + a republished remote WOULD have
mixed old-prefix/new-suffix bytes into a file that passes the size
check AND the GGUF-header check. The proof, end-to-end against the
real CDN this session: a 1,000-byte garbage `.part` + a stale sidecar
→ the CDN served the 206 → the client resumed → the mixed file's
sha256 mismatched the published hash → **the wrong bytes were deleted,
nothing was installed**. The sha256 is not a nicety; it is the only
corruption gate that binds this CDN. (The V0.6.60 defense stays — it
costs nothing and binds spec-compliant servers — but the hash is the
guarantee.)

## The release — two pieces

1. **THE OFF-THREAD SCAN (the transcribe dialog):**
   `_refresh_cpp_models` now spawns a SimpleWorker whose closure does
   the settings read + directory walk + GGUF header reads; the combo
   shows a "(scanning…)" placeholder (signals blocked) and populates
   in the new `_on_cpp_models_scanned` slot when the result lands —
   the V0.6.59 populate contract unchanged (saved-first, selected,
   blockSignals, per-item tooltips, the empty-placeholder offering the
   download). Re-entry is guarded by PLAIN-PYTHON flags — deliberately
   not `worker.is_running()`: the auto-deleteLater'd wrapper must
   never be touched again (PySide6 raises RuntimeError on the deleted
   C++ object; the second 🔄 click would crash). A refresh requested
   mid-scan (the operator browsed to a file while the dialog-open scan
   was still walking a big Downloads dir) is REMEMBERED
   (`_cpp_scan_pending`) and re-dispatched when the in-flight scan
   lands — the picked model can no longer be swallowed. The worker
   failure path releases the flag (a stuck placeholder would brick 🔄)
   and leaves an honest retryable state. The closure touches NO
   dialog state — pinned by AST TWO ways (no `self.` text AND its
   free variables must all be module-level imports), and the catalog
   calls are pinned to live ONLY inside the closure (a decorative
   worker + a synchronous scan would fail the pin).
2. **THE SHA256 CONTRACT (the downloader leaf + catalog):** every
   DOWNLOAD_CATALOG entry carries the published sha256 (the HF API's
   `lfs.sha256` — the content hash; mechanism PROVEN live:
   whisper-tiny-Q4_K_M.gguf downloaded in full, 43,621,792 bytes, its
   sha256 matched the API value byte-for-byte). `download()` gained
   `expected_sha256=`: the stream is hashed incrementally as chunks
   land; the resume path hashes the `.part` prefix FIRST (chunked,
   cancellable — a 1.6 GB prefix read must never ignore the ✖ button);
   the 416 "already-complete" recovery hash-verifies before the rename;
   the recursive 416 restart FORWARDS the hash; and a mismatch names
   BOTH digests in the error and DELETES the wrong bytes (resuming
   garbage would reproduce garbage). The success message now states
   the proof: "sha256: verified — byte-identical to the published
   file" (or honestly "not checked" when no hash is known).

## The fresh-eyes review (two parallel read-only reviewers, pre-release)

Both verdicts: **RELEASE READY.** Every SHOULD-FIX was fixed BEFORE
shipping, each with a pin: the unpinned recursive-416-restart hash
forwarding (now pinned: the shrunk-remote scenario + a hash); the
unpinned resume-route mismatch deletion (now pinned: a corrupted
`.part` prefix + a matching etag → 206 → the combined digest is named
in the error and everything is deleted); the cancel-unresponsiveness
during prefix hashing (`_hash_file` now honors `should_cancel`); the
416-recovery unlink sharing a `try` with the rename (a failing unlink
after a successful rename no longer reports ok=False); the subsumed
disjunct + the misleading test name; and three dialog-pin
strengthenings (the free-variable pin, the AST-identity
catalog-calls-in-closure pin, the write-only `_cpp_scan_worker` pin).

## The rig flow after V0.6.61

Unchanged on the surface — open the dialog, the GGUF combo populates
(now without ever touching the UI thread; on a slow disk you see
"(scanning…)" for a moment), pick the model, Transcribe. Get-models
downloads now end with "sha256: verified — byte-identical to the
published file". The failure that can no longer happen: a corrupted
1.6 GB download that looks fine (right size, valid header) and
crashes the CLI minutes into the first run.

## Remaining boundary (honest)

Sandbox-only: no PySide6 — the dialog wiring is AST-pinned, the leaf
behaviorally tested. Accepted risks (documented): a server that
omits Content-Length entirely (total=None) + truncation mid-body
falls to the hash gate and deletes instead of keeping-for-resume
(HF's CDN always sends Content-Length; unreachable in practice); the
scan thread has no app-quit guard (the house-shared worker pattern;
the window is seconds at dialog open). The rig validation item
stands: the first dialog open + first download remain the final
visual checks.
