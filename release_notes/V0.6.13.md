# V0.6.13 — the llama.cpp-first policy extended to the services: the TTS text normalizer, the transcribe summary, and the Podcast Maker script generator wired ("they find LLM on Ollama only") — 7,666 P / 0 F

## The user report

> "ALSO TAKE NOTE THAT tts , TRANSCRIBE SERVICE AND PODCAST HAVE SAME
> PROBLEM, THEY FIND LLM ON OLLAMA ONLY"

The V0.6.12 policy (Ollama = the always-on default; llama-server started
deliberately — so "llama.cpp is up" MEANS "route to it and the model it
serves") was wired into Packets of Knowledge and the new-output riders.
This release extends it to the three services the operator named. One
new predicate, `is_local_url()` in `core/llm/local_fallback.py`: the
URL-only sites (podcast `ollama_url`, TTS `tts.normalize_endpoint`)
consult the policy ONLY when their configured target is loopback — a
deliberately-configured remote endpoint (a LAN Ollama, a hosted
OpenAI-compatible URL) passes through untouched, the same treatment
cloud providers get. Kill switch unchanged:
`local.llamacpp_first = false` restores the pre-V0.6.12 behavior at
every wired site.

## The three wirings

- **The Podcast Maker script generator (`generate_podcast_script` +
  `_generate_podcast_title`):** the tool is Ollama-native (raw
  `/api/generate`), so the policy applies when its `ollama_url` is
  LOCAL: a live llama-server takes over BOTH the script call and the
  title call — the OpenAI-compat `{base}/chat/completions` branch with
  the DETECTED served model (V0.4.30 precedent: detected wins over the
  dialog's pick) + Bearer key; dead → the configured Ollama path,
  byte-identical to V0.6.12 (payload pinned: num_predict 4096 /
  num_ctx 131072, no auth header). A connection error now names the
  backend (`Could not connect to llama.cpp at … Is llama-server
  running?`) instead of the raw urllib3 blob.
- **The transcribe summary (`summarize_transcript`):** the decision
  runs before `create_provider()` — takeover sets provider=llamacpp
  and passes the DETECTED served model to `complete_streaming()`;
  cloud selections are never probed; dead llama.cpp leaves the
  configured provider path byte-identical.
- **The TTS text normalizer (`create_normalizer_from_settings` — also
  the podcast-audio normalize step) + the Settings→TTS "Test
  normalization" button:** the TextNormalizer already speaks
  OpenAI-compat, so a takeover simply points it at the live
  llama-server (endpoint + detected model + Bearer key) — and SKIPS
  the Ollama `/api/tags` model discovery, which with Ollama down used
  to fail and DISABLE normalization (the reported "finds LLM on Ollama
  only" defect in its sharpest form). The served model is NOT
  persisted to `tts.normalize_model` (that setting names the
  configured backend's model for the no-llama.cpp case). The settings
  test button resolves the policy in its WORKER (never the UI thread —
  the W-b8/W-b11 offload contracts are pinned unchanged, widget-free
  worker body, main-thread snapshot).

## The completion bug caught in the inherited working tree

The previous session left this wiring uncommitted and INCOMPLETE: the
title call site passed `llamacpp=_llamacpp` into
`_generate_podcast_title` BEFORE the parameter existed — every podcast
generation would have crashed with `TypeError: unexpected keyword
argument` at the title step (after generating the whole script). The
parameter + routing were completed this session and pinned by direct
tests (the `llamacpp=None` default keeps the Ollama path byte-identical;
the takeover branch routes to `/chat/completions` with `max_tokens 50`;
the pre-existing fail-soft — an exception in the title call falls back
to the first content line's words — survives the takeover).

## Rig determinism

The existing tests that now flow through the wired sites (the
transcribe/podcast e2e file, the TTS secrets-wiring test) pin

a real llama-server on 8080. Tests that WANT the live :3031 shim
override the pin explicitly.
