## The exact status-verification logic

* **Locals (Ollama / llama.cpp / LM Studio):** the pre-existing poll
  loop's verdicts — loopback GETs against the CONFIGURED endpoint URLs
  (never assumed ports), run off the UI thread, applied on the main
  thread. `LocalLLMStatus` gains a `models` tuple (the evidence): Ollama's
  `/api/tags` is authoritative (an empty listing with a configured model
  → "Model unavailable"), while llama.cpp/LM Studio listings may be
  absent on older builds (an empty listing is NOT evidence — the state
  stays "Connected" when the server answers).
* **API providers (OpenAI-compatible / Claude):** ONE tiny real request —
  the app's own pre-flight verifier `test_cloud_connection` for the
  OpenAI shape, and a Claude twin using `ClaudeProvider`'s exact header
  contract (`x-api-key` + `anthropic-version`) for Anthropic. A missing
  base URL / key / model is "Not configured" (gray) — a config gap is
  never a connectivity result; a connection failure, 401/403, or bad
  response is "API unavailable" (red) with the distinguishing detail in
  the tooltip. Triggers: startup + a Settings close. Never polled on a
  timer (spec §5.2: "Avoid aggressive polling").
* **The wizard's lifecycle** ("Converting…") keeps its own DISTINCT
  transient word beside the connection state and clears when the dialog
  closes — "the UI is running" is never conflated with "AI operations
  can run" (spec §5.1). No `"Ready"` string remains anywhere in the app.
* **Non-blocking, everywhere:** every check runs on a `SimpleWorker`;
  overlapping checks are skipped; exploded probes keep the last painted
  state (fail-soft, quiet log).
