# V0.6.15 — the VibeVoice podcast diagnostics + compatibility release ("it generated text by llm, but vibevoice had error") — 7,641 P / 0 F

## The user report

> "Another Error, the app has problem with vibevoice, podcast tool, it
> generated text by llm, but vibevoice had error."

The V0.6.13 llama.cpp-first wiring fixed the script step — the Podcast
Maker's LLM now generates the text through llama.cpp or Ollama. The
failure moved one stage deeper: the VibeVoice synthesis. The live log
could not say why — every failure surfaced as a one-line error string
while the subprocess's actual traceback (the WHY) was dropped on the
floor. This release makes every VibeVoice failure mode name itself, and
fixes the two compatibility gaps that can actually break the chain on a
rig whose torch/vibevoice install has drifted.

## What was wrong (found by auditing + live-simulating the whole chain)

The session rebuilt the sandbox (env reset again), then ran the REAL
`VibeVoiceEngine` → REAL `_vibevoice_subprocess.py` protocol end-to-end
against a stub torch/vibevoice stack — the handshake, the minimal-env
spawn, the preset load, generation, the teardown. The protocol itself
passes. The gaps were around it:

1. **The traceback was dropped.** The subprocess sends
   `{"status": "error", "error": …, "traceback": …}` — the engine raised
   with the error string only. The operator's paste-back never contained
   the actual cause (a CUDA OOM, an import failure, a preset problem all
   look identical in the report).
2. **The preset load was single-path.** `torch.load(weights_only=False)`
   unconditionally — while the official VibeVoice demo loads with
   `weights_only=True` inside `torch.serialization.safe_globals`, and
   torch < 2.6 has no `safe_globals` at all (the context manager itself
   raises AttributeError → a hard generate error).
3. **A CPU load was silent.** If CUDA is invisible in the subprocess
   (DLL layout, torch build), the model loads on CPU — ~100× slower —
   and every podcast line then dies at the 600 s timeout with nothing in
   the log naming the cause while there was time to cancel.
4. **No free-VRAM check.** The rig runs llama-server for the LLM step of
   the same podcast; when it holds the card, the 2.6 GB VibeVoice load
   dies on CUDA out-of-memory with nothing naming the likely holder.
5. **The podcast log never showed the config truth** — whether the
   VibeVoice model path and voices dir were even valid.

## The fixes (3 runtime files, +19 tests)

- **`core/tts/vibevoice_engine.py`** — the load-error and generate-error
  paths now forward the subprocess traceback to the live log (📋 lines at
  ERROR level); a `No module named 'vibevoice'` load error appends the
  install command (`git clone … && pip install -e ".[streamingtts]"`);
  a `device: cpu` loading status logs the CPU WARNING (naming the 600 s
  timeout consequence + the `~/.elixir/gpu_probe.log` path); a new
  `_preflight_vram()` helper (fail-soft — no torch in the parent means
  no check, never a failure) logs free VRAM and warns under 3.5 GB
  naming llama.cpp / Ollama as the likely holders; the generate-error
  kill-reason truncation widened 80 → 200 chars. The V11.57
  no-restart policy and the V18.20.4.4 kill-before-raise contract are
  byte-identical (pinned).
- **`core/tts/_vibevoice_subprocess.py`** — the voice-preset load moved
  into `_load_voice_preset()` with a 3-step fallback chain: the official
  `weights_only=True` + `safe_globals` path FIRST, the legacy
  `weights_only=False` on failure, and a plain `torch.load` when
  `safe_globals` doesn't exist (torch < 2.6); the CUDA load path now
  reports FREE VRAM alongside total (`torch.cuda.mem_get_info`) and
  warns under ~3.5 GB; the load and generate exception handlers write
  the FULL traceback to stderr (the parent's drain logs it live — the
  JSON's 500-char copy is no longer the only record).
- **`core/podcast/audio_generator.py`** — a new
  `_log_vibevoice_config()` helper logs the model path and voices dir
  with their existence (`— OK` / `— NOT FOUND` / `(not set)`) before
  the first spawn, so every podcast log carries the config truth.

## The tests (tests/test_v0615_vibevoice_diagnostics.py — 19 new)

- Engine behavioral (the `_FakeProc` pattern from test_v182044):
  traceback forwarding on both error paths, the install-hint append
  (and its absence for other errors), the CPU warning (and no warning
  on cuda), the VRAM pre-flight low/healthy/no-torch cases, and the
  kill-before-raise contract surviving.
- Subprocess source pins: the fallback-chain ORDER (official first),
  the torch < 2.6 AttributeError branch, the free-VRAM report, the
  stderr traceback on both handlers.
- Audio generator behavioral: the config-truth log (valid / missing /
  empty paths), the empty-path error contract unchanged.
- **One LIVE protocol test**: spawns the REAL `_vibevoice_subprocess.py`
  through the REAL engine against a stub torch/vibevoice tree built in
  tmp_path — the full spawn→handshake→preset-load (via the new
  weights_only=True path)→generate→save→teardown chain, no 2.6 GB
  model, no GPU. This is the test that pins the whole protocol the rig
  runs.

## Test path (what the operator will see on the rig)

1. Run the Podcast Maker with a VibeVoice voice. The log now shows, in
   order: the VibeVoice model + voices dir paths with OK/NOT FOUND, the
   free VRAM line (with the llama.cpp/Ollama warning if low), the
   load device (with the CPU warning if CUDA is invisible), and — if
   anything fails — the full 📋 traceback instead of a one-line mystery.
2. If the failure persists, the log line(s) around the failure now
   contain the actual cause; paste those back and the fix will be
   immediate instead of another round of blind fixes.
3. If llama-server is holding the GPU when the podcast starts, expect
   the low-VRAM WARNING — free VRAM before the VibeVoice step (or
   generate the audio with Kokoro voices, which need far less).
