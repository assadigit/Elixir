# V0.6.57 — "Why model is working on CPU?" answered with DATA, not guesses — a `--list-devices` pre-flight names the backends actually compiled into transcribe-cli.exe BEFORE the model loads, live nvidia-smi lines show the GPU working (or idle) every 30s, the run config (model size / audio duration / exact command) is on record, and the end-of-run backend verdict warns loudly when the CLI computed on CPU — 55 new pins / 204 P affected sweep / 0 regressions

## The user report

> "Why model is working on cpu? I have weak cpu and strong GPU!"
> "...it used to transcribe in less than a minute by using the same
> transcribe.cpp! Something is broken"

(With a real 15-minute 256 MB video silent for 3+ minutes in the V0.6.56
live log, and — decisively — the upstream repo link:
github.com/handy-computer/transcribe.cpp.)

## What the V0.6.56 log had already proven

The live log did its job: heartbeats ticked, the gap grew, the
engine-silent hint fired — the CLI was alive and working but printing
NOTHING. What it could NOT answer: **which device was computing**. The
operator guessed CPU from Task Manager; the log had no evidence either
way. V0.6.57 closes exactly that gap.

## The diagnosis (three facts, evidence-first)

1. **The app did not switch the CLI to CPU.** Git archaeology: the CLI
   command (`[exe] -m <model> [-l lang] <wav>`) is byte-identical since
   V0.6.40 — V0.6.56 changed only HOW output is read (Popen + reader
   threads instead of `capture_output=True`), never what the child
   receives. Same exe, same args, same env, same stdin.
2. **The CLI is silent by design while it works.** The upstream CLI
   source (`examples/cli/main.cpp`, which the operator's repo link made
   readable) prints its `audio:` block, loads the model SILENTLY, and
   only then prints `model: … -> ok` + `backend: <kind>` — the whole
   summary lands at the END (the V0.6.52 parser fixture agrees:
   `realtime: 0.4x` can only be computed after the run). A 3-minute
   silent log is the model load in progress, not a hang.
3. **The most probable root cause is the exe itself.** The upstream
   build docs: a plain `cmake -B build` on Windows is **CPU-ONLY** —
   Vulkan requires `-DTRANSCRIBE_VULKAN=ON`. The default `auto`
   backend then silently picks CPU. A `git pull` + plain rebuild (the
   repo is very active) drops the GPU without a word — matching
   "it used to be fast with the same transcribe.cpp" perfectly: same
   project, different binary. The app's "(Vulkan GPU)" label was an
   ASSUMPTION since V0.6.40, never a verified fact.

## The fix — four diagnostics, all in the live log

**1. The `--list-devices` pre-flight (seconds, no model load).** The
upstream CLI supports `--list-devices`: it registers the backends
compiled INTO the exe and lists every device with its memory. The
engine now runs it BEFORE the 3 GB model starts loading and logs:

- a GPU is registered → `  [DEVICES] GPU device registered: [0]
  NVIDIA GeForce RTX 3060 (vulkan, 10.5 GiB free) — the CLI
  auto-selects it`
- only CPU devices → `  [DEVICES] NO GPU device registered (1
  device(s), all CPU) — this transcribe-cli.exe will compute on CPU`
  plus a WARNING with the exact fix: `cmake -B build
  -DTRANSCRIBE_VULKAN=ON` (needs the Vulkan SDK; see
  docs/build-windows.md) or switch the engine to faster-whisper;
- an exe predating the flag → one honest "listing unavailable" line.

**2. Live GPU telemetry.** Every 30s while the CLI runs, a
best-effort `nvidia-smi` query lands in the log: `  [GPU] GPU: 96%
util, 3.3 GB VRAM used`. Rising VRAM during model load is proof of
progress even at 0% util; util at/below 5% is flagged `(idle —
sustained 0% while the CLI works points at CPU/fallback)`. The probe
rides the worker thread's existing 0.5s poll loop (never the UI
thread), is killed by a 2s timeout (never hangs on a wedged driver),
and on the first failure logs ONE "probe unavailable" line and
disables itself — no spam, no crash, `None` is a legitimate answer.

**3. The run config on record.** Before `[RUN]` the log now carries:

- `  [MODEL] whisper-large-v3-Q8_0.gguf (3.0 GB) - the model file
  reloads on every run` — the #1 silent-time cost, finally visible
  (a 3 GB model reload explains minutes of quiet by itself);
- `  [AUDIO] 15:02 of audio to transcribe` — from the stdlib `wave`
  reader on the temp WAV; 15 minutes of audio is never a 1-minute
  run, whatever the old anecdote says;
- `  [CMD] <the exact command line>` — the manual-repro ground truth
  to compare against the owner's transcribe.bat.

**4. Honest labels + the end verdict.** The `[RUN]` status is now
built from the pre-flight result — `(vulkan)` when a GPU device is
registered, `(CPU ONLY - no GPU device in this exe)` when not —
instead of the hardcoded "(Vulkan GPU)" assumption. At the end of the
run the CLI's own `backend:` line (already parsed since V0.6.52) gets
a WARNING when it says CPU, naming the real fix. The heartbeat's
silence hint is engine-aware now: transcribe.cpp runs explain the
CLI's end-only printing and point at the `[GPU]` lines; the old
"whisper model load / LLM on CPU" text survives verbatim for
LLM-phase runs — on the triggering raw-transcript-only run it was
actively misleading (there was no LLM at all).

**Caught mid-release by the operator's repo link:** the draft warning
named `-DGGML_VULKAN=ON` — whisper.cpp's flag, wrong for this
project. transcribe.cpp uses `-DTRANSCRIBE_VULKAN=ON`. Both warning
strings now pin the correct flag, and a test bans `GGML_VULKAN` from
them forever.

## What the operator should do on the rig

1. Update to V0.6.57 and run a SHORT clip. Within seconds the log's
   `[DEVICES]` line states whether this exe has a GPU backend.
2. If it says NO GPU: `winget install KhronosGroup.VulkanSDK`, open a
   NEW terminal, `cmake -B build -DTRANSCRIBE_VULKAN=ON`, `cmake
   --build build --target transcribe-cli --config Release` (upstream
   docs/build-windows.md). Verify with `transcribe-cli.exe
   --list-devices`.
3. Check the `[MODEL]` line: a 3 GB large-v3 reloads on EVERY run —
   minutes of model load per run by design. If the old sub-minute
   runs used a smaller model (the Model button / settings), that
   difference — not a regression — is the wait.

## Rig-only boundary (the honest limit)

The sandbox has no NVIDIA GPU and no Windows transcribe-cli.exe, so
the nvidia-smi path and the real `--list-devices` output are exercised
through injected runners + the upstream main.cpp format; the rig's
first real run is the final validation. The pre-flight's `None` path
(the exe predating `--list-devices`) keeps the historical label
rather than guessing.
