# V0.6.5 — the RTL outputs (md · docx · PDF, VLM-verified) · the LLM-structured Markdown Styler · the translation active-LLM fallback · the GitHub release system

Three user-reported fixes and one process change. 46 new tests; every PDF claim verified VISUALLY (rendered pages checked with a vision model — right-aligned, correctly shaped Persian, bullets on the right, no missing glyphs).

## 1. The RTL fix — "the pdf conversion of a Farsi text works, but it still LTRs the content… it's fine in md and docx"

Root cause: NONE of the three writers had any direction handling. One content-agnostic detector (`utils/rtl.py` — letters-only script ratio, ≥35% RTL letters ⇒ RTL document) now threads through every format via `write_output`'s auto-detect:

- **md** — the Obsidian `dir: rtl` front-matter property (merged into existing front-matter, never duplicated).
- **docx** — the `w:bidi` paragraph property + right alignment on EVERY paragraph (headings, bullets, quotes): Word reorders runs and renders bullets on the right.
- **pdf (WeasyPrint)** — `direction: rtl` + right alignment + the bundled **Vazirmatn** typeface via `@font-face` (SIL OFL — the standard Persian font; the default Helvetica/Segoe stack has no Arabic glyphs). Pango does the real bidi + shaping.
- **pdf (ReportLab fallback)** — arabic_reshaper + python-bidi produce the visual character order per fragment (ReportLab draws exactly the bytes it's given), right-aligned styles, bullets hanging on the right edge, the registered Vazirmatn TTFs. Both libraries are now in `requirements.txt` (pure-Python, tiny) with graceful degrade + WARNING when absent.
- The translation tool's Persian outputs gain `dir: rtl` automatically (same `write_output`).

## 2. The Markdown Styler — "it needs LLM intervention: FIRST the LLM must scan the article and find headings (generate one if there isn't), THEN stylize it into the Obsidian style"

Exactly that pipeline (`core/summarisation/markdown_styler.py`):

- **Phase 1 — the scan (LLM):** one call returns STRICT JSON — the article's real detected title (or a fitting GENERATED one when there is none — no more "Untitled Note"), a 1-2 sentence tldr, key concepts, tags, `is_rtl`, and the sections with their own headings + levels + cleaned content. The prompt demands the original wording: the LLM restructures, it never rewrites.
- **Phase 2 — the assembly (pure Python):** front-matter (title/date/tags/dir), the `> [!tldr] Summary` and `> [!info] Key Concepts` callouts, `##`/`###` sections with collapsed blank-line runs (the "lots of spaces" report).
- **Robustness:** lenient JSON recovery (fences, prose wrappers, trailing commas); one JSON-only repair retry; on failure the dialog falls back to the V11.71.0 deterministic regex path with a ⚠️ status — never an error dialog for a model miss. The LLM call rides a worker thread (never the UI thread); the checkbox turns it off for the instant offline path.

Live-verified through the real provider: a raw Persian article with no headings produced the title "کلود استیم: مشکلات و راه‌حل‌ها", all four section headings detected, RTL flag set, proper Obsidian note assembled.

## 3. The translation fallback — "fall back to the current active LLM (ollama or llama.cpp) when no dedicated translation model is found"

`TranslationEngine` gains a provider-backed `llm_complete` transport: when no translategemma-family model exists, every line call routes through the ACTIVE provider (`create_provider` — ollama, llama.cpp, OpenAI-compat, Claude all speak it) instead of the raw Ollama `/api/generate` POST that a llama.cpp backend can't answer. A user-TYPED model stays authoritative; only the unreachable seeded default swaps to the active model. The status line says exactly which fallback fired.
