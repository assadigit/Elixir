# V0.6.12 — the llama.cpp-first fallback release: "Packets of Knowledge is not connected to llama.cpp" fixed + the new-output riders' silent llama.cpp skip fixed — 7,632 P / 0 F

## The user report

> "Packets of knowledge is not connected to llama.cpp so it doesnt work.
> it gives this error: ❌ LLM call failed: HTTPConnectionPool(host='localhost',
> port=11434): Max retries exceeded … WinError 10061 …
> can't we have a rule for fall back llm? look my ollama is always on or
> mostly, because of auto startup item. but i turn on my llama.cpp casually.
> (only when I need) so app must first look for llama.cpp if it's on, it
> means I want that model to be selected, add this policy."

Two real defects were under that report, plus the policy request:

1. **Packets of Knowledge never read the llama.cpp settings at all.**
   `_call_llm` read only `summarisation.endpoint` (default
   `http://localhost:11434/v1`) for every non-cloud provider — so with
   provider=llamacpp saved, the tool still POSTed to Ollama's
   `/api/generate`. When Ollama was also off (the report's WinError
   10061 — connection actively refused), the run died printing the raw
   urllib3 `HTTPConnectionPool` wall of text.
2. **The new-output riders (Executive Briefing / Podcast Script /
   Flashcards) silently skipped on a llama.cpp rig.**
   `OutputGeneratorBase._call_llm_once` branched only on ollama /
   openrouter-openai-openai_compatible / freellmapi — provider
   "llamacpp" (**the fresh-install default**) matched NO branch and
   returned None; the riders' deterministic fallbacks fired, so nothing
   LOOKED broken while every LLM synthesis quietly never happened.

## The policy (as ordered, verbatim intent)

**Ollama is the always-on default; llama-server is started deliberately
— so "llama.cpp is up" MEANS "route to it and the model it serves";
otherwise fall back to the configured backend.**

`core/llm/local_fallback.py` — `decide_llamacpp_first()`: one shared
decision for every raw-request LOCAL call site. A live llama.cpp at
`summarisation.llamacpp_base_url` (GET /v1/models, the V0.4.30 factory
precedent: the DETECTED served model wins over the configured name) →
takeover with the served model + the Bearer key (honored when
llama-server runs `--api-key`, ignored otherwise). Dead → the call
site's configured path runs byte-identical to V0.6.11. Cloud selections
are never probed, never overridden. The probe is TTL-cached (30 s,
lock-guarded — the packets generator resolves once per packet, 5+ times
a run). **Kill switch: `local.llamacpp_first = false`** restores the
pre-V0.6.12 behavior everywhere.

Scope boundary (deliberate, honest): the policy is consulted by the
raw-request tool call sites (Packets, the riders). The main conversion
pipeline keeps its wizard-selected provider — its VRAM budget gate
(V0.6.9, restored) is confirmed against the CONFIGURED model, and a
silent mid-run swap to a different llama.cpp model would bypass that
confirmed budget. Extending the policy to the pipeline is an operator
decision that must be made WITH the VRAM policy, not under it.

## The fixes

- **Packets (`ea0c542`):** the decision runs before dispatch — takeover
  POSTs `{llamacpp_base_url}/chat/completions` (the OpenAI-compatible
  SSE branch llama-server speaks) with the detected model + key; dead →
  the configured endpoint, byte-identical (the native :11434
  `/api/generate` branch for Ollama endpoints — pinned with
  no-explicit-headers assertions). A `ConnectionError` now logs
  `❌ Cannot reach <url> — is Ollama running?` (or llama.cpp / the
  configured backend, by target) instead of the raw urllib3 blob;
  control flow unchanged (first failure returns None, no retry). The
  takeover/dead note logs once per run (`🦙 llama.cpp detected at …` /
  `🦙 llama.cpp not reachable at … — using the configured backend`) so
  the tool log always says WHICH backend took the call.
- **Riders (`d6277ec`):** same decision at the top of `_call_llm_once`
  + a proper `llamacpp` branch for the dead-server case (the
  configured llamacpp URL gets the call instead of the silent None).
  The silent-skip defect is pinned by a characterization test that was
  RED on the pre-fix code (`call_once()` returned None with
  provider=llamacpp) and GREEN after.
- **Live-test determinism:** the :3031 shim fixture pins
  `llamacpp_base_url` at a dead port so `TestPacketsGeneratorLiveShim`
  routes at the shim even on a rig with a real llama-server on 8080
  (the test's intent — the OpenAI-compat SSE branch — unchanged).
