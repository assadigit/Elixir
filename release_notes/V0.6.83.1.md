## Context (the post-tag `1a4a6dc`, previously documented only in its commit message)

The CI Test job now installs the Qt runtime libs
(`libegl1 libgl1 libxkbcommon0 libdbus-1-3 libxcb-cursor0`), so the
PySide6-importing tests — the ~90 that ImportError'd on every run since
the V0.6.82 era, environment failures never code regressions — finally
RUN on CI. That enablement unmasked a latent, order-dependent suite
defect this hotfix repairs.

## The crash №1 (SIGABRT at 47%, exit 134)

The first Qt-enabled run (run 226 on `1a4a6dc`) died mid-
`tests/test_v00420_crashfixes.py::test_icon_is_horizontally_centered`
with `Fatal Python error: Aborted` — the whole pytest process killed, no
summary line ever printed.

**Root cause** (bisected to a 3-file reproducer, `test_m1_theme_tokens +
test_m2_dashboard + test_v00420`, then minimized to a standalone script):
`test_m1_theme_tokens.py::TestQtBehaviour::test_icon_home_renders_non_null`
created a **`QGuiApplication`** — not a `QApplication` — and shiboken
keeps the app singleton alive for the rest of the process. Every later
behavioural test's `QApplication.instance() or QApplication([])` then
short-circuits on that wrong-typed instance (it is truthy), so no real
QApplication ever exists, and the first `QWidget()` hits Qt's qFatal
*"QWidget: Cannot create a QWidget without QApplication"* → SIGABRT.

**Fix:** that one test now creates a **`QApplication`** (a subclass —
icon/`QPixmap` rendering is identical) via the same offscreen argv,
keeping the process un-poisoned for every widget test that follows
(`test_v00420`, `test_v0683`, …). The class's availability guard checks
`PySide6.QtWidgets` (what `theme.py` itself imports).

## The crash №2 (SIGSEGV, exit 139)

With crash 1 repaired, the full suite ran on — and died again at 61%,
this time a segmentation fault inside the podcast e2e's real-ffmpeg
`subprocess` fork, again with no summary.

**Root cause** (isolated to standalone class runs, no fork needed): the
behavioural dialog tests create top-level dialogs that are never closed
or deleted — the Python name goes out of scope while the C++ QWidget
lives on under the QApplication. At interpreter shutdown Shiboken then
destroys those widgets around/after the QApplication itself — the
classic PySide6 use-after-free. Reproduced deterministically: each class
ALONE passes all its tests and then segfaults at exit; the corrupted
heap also detonates at later forks. (`close()` alone is NOT enough, and
close() is also WRONG here: the dialogs' closeEvent guards raise a modal
"a background task is still running" QMessageBox no headless run can
answer — teardown must `hide()` + `deleteLater()` and drain the loop.)

**Fix:** a new suite-wide autouse fixture in `tests/conftest.py`
(`_dispose_qt_toplevel_widgets`) — after EVERY test, when a QApplication
exists, hide + `deleteLater` every top-level widget and drain ONLY the
DeferredDelete events (a plain `processEvents()` drain delivers
still-queued application events onto the half-torn-down dialog — a third
crash, SIGABRT inside `image_extractor_dialog._on_done`, found and
fixed during this very hotfix's verification). The QApplication
singleton is deliberately kept; pure tests pay one guarded import check.
