# V0.6.64 — "remove piper entirely, keep tesseract": the Piper TTS engine is GONE — the binary-subprocess Persian engine, its voice catalog + HuggingFace downloader, the settings keys, the UI pickers, the dependency checks, the `piper-tts` extra, and its 14 tests — while every other Persian route (Coqui XTTS v2, Kokoro, Sherpa) is untouched · plus the CI-green cleanup: 14 of the 15 lint findings fixed + all 26 format-drift files formatted + CI's test job now installs the pinned `requirements.lock` closure instead of unpinned `requirements.txt`

## The decision this ships

The standing question (remaining-surface item 4) was what to do about the
two optional externals the installer does not bundle: **Tesseract** (OCR)
and **Piper** (Persian TTS) — bundle them, give them an Ollama-style
download-link flow, or something else. The owner's decision, verbatim:

> "Remove piper entirely. keep tesseract."

So: Piper is deleted from the application, not bundled and not given a
download flow. Tesseract stays exactly as it is (not bundled; the app
shows its friendly message when it is missing).

## Why this is safe — Piper was already retired in practice

Piper was the **legacy** Persian engine: a `piper.exe` binary called
through `subprocess` (the Python `piper_phonemize` package has no Windows
wheels), wired through the V4.x-era `TTSRouter` used by the intro-podcast
and packets-audio legacy paths. The **modern** paths never used it:

- The **TTS tool** (`tts_service_dialog.py`) routes Farsi to **Kokoro**
  (V11.44.0 default) and **Sherpa** (`sherpa:` voice prefix).
- The **podcast generator** (`core/podcast/audio_generator.py`) routes
  Farsi to **Kokoro** — its own docstring has said "Removed … Piper"
  since V11.40.0.

After V0.6.64 the legacy router's Persian route is **Coqui XTTS v2**
(the only remaining fa engine there), which was already the
quality-first choice (`fa_engine: coqui`) since V10.36.0.

## What was removed (the full inventory)

- `core/tts/engine.py`: the `PiperEngine` class, `PIPER_SYNTH_TIMEOUT_S`
  (W-c8), the router's `piper` property / `_piper*` fields, and the
  `piper_binary` / `piper_voices_dir` / `fa_engine` constructor params.
  `persian_engine()` now returns Coqui (fail-soft at synthesis, as
  before).
- `core/tts/voices.py`: `PIPER_FA_VOICES`, `PIPER_FA_DEFAULT`,
  `piper_voice_label`, `piper_voice_repo`, `ensure_piper_voice`
  (the HuggingFace .onnx downloader — `huggingface_hub` itself STAYS:
  VibeVoice/Qwen3-TTS/Persian-VITS use it).
- `core/tts/engine_cache.py`: `get_piper_engine` (had **zero** runtime
  callers — only tests).
- `core/tts/__init__.py`: the Piper exports.
- `utils/settings.py`: the `tts.piper_binary` / `tts.fa_engine` /
  `tts.fa_host_{a,b}_voice` defaults are gone, `tts.fa_voice`'s default
  is `""` (was a Piper voice id), and a V0.6.64 migration **pops the
  dead keys from older settings.json files** and resets a stale
  `fa_IR-*` voice id to the Coqui-speaker default (no more "Unknown
  setting" warnings).
- `core/system/dependency_checker.py`: the `piper` import check + the
  `tts.piper_binary` existence probe (Tesseract's checks untouched).
- `core/vram_calculator.py`: the 0.1 GB `piper` estimate.
- UI (`tts_page.py`, `podcast_page.py`, `defaults_section.py`,
  `dependencies_page.py`): the Persian-voice combo, the Piper binary
  picker + connectivity dot, the Piper/Coqui engine selector, the
  "Piper" default-engine combo entry. The Settings → TTS Persian
  **preview** now rides Coqui XTTS v2 (model/speaker/voice-sample
  snapshot instead of the old binary snapshot).
- Messages/docstrings: qwen/vibevoice "Use the Kokoro voices instead"
  (was "Kokoro or Piper"), the pipeline/registry subtitles
  ("FA→Coqui XTTS v2"), the TTS diagnostics log lines.
- `pyproject.toml`: `piper-tts` removed from the `[tts]` extra.
- **Kept, deliberately:** the Sherpa engine's `vits-piper-*` model
  names — those are literal sherpa-onnx model-file URLs (a different
  runtime), not the Piper engine.

## Risks and unverified parts (honest list)

- **Settings preview for Persian** now needs `pip install TTS` (Coqui)
  where it previously needed the Piper binary — a source-install
  feature either way; the installed (packaged) app shows a clear error.
- Users with `fa_engine: "piper"` or `fa_voice: "fa_IR-…"` in an old
  `settings.json`: the V0.6.64 migration drops/resets those keys on
  next launch — verified by unit tests, not on a real rig.
- The **installed-app** paths (real conversion → Persian podcast audio,
  the Settings → TTS page render) remain rig-checklist items — all
  rendering here is offscreen.
- CI's pytest job is drift-proofed but still red on the documented
  environment-dependent families; **pip-audit still fails on 7 lock
  pins with known vulns** (aiohttp 3.14.3→3.14.4, certifi→2026.10.19,
  multidict 6.9.0→6.9.1, opentelemetry-api 1.44.0→1.45.1, pillow
  12.3.0→13.0.0 (~35 findings, a MAJOR bump), pyjwt 2.14.0→2.15.0,
  pypdf 6.19.0→6.21.1). Upgrading the pins changes the verified
  environment — the owner's decision (upgrade vs documented waivers),
  not taken unilaterally.
