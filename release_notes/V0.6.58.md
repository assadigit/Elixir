## What the V0.6.57 telemetry had already proven

The GPU question is ANSWERED: `[GPU] 99% util` with VRAM full, a
vulkan device registered pre-flight — the run computes on the GPU, is
not hung, and is not on the CPU. What the log still could not answer:
**how long should this take, is the app slower than the bat, and what
would make it fast again?**

## The diagnosis (the bat + the upstream source, evidence-first)

1. **The app runs the bat's exact command.** The uploaded
   `transcribe.bat` line 25 is `"%CLI%" -m "%MODEL%" "%WAV%"` — and
   the app's `[CMD]` is `transcribe-cli.exe -m
   whisper-large-v3-Q8_0.gguf <wav>` with zero extra flags (language
   auto). Same exe, same model, same 16 kHz mono conversion (the bat's
   ffmpeg line `-ar 16000 -ac 1` is the engine's `_convert_to_wav16k`
   exactly). Any speed difference vs the bat cannot be the command
   line — but "identical" was an eyeball claim, not a computed one.
2. **The CLI cannot behave differently under the app.** The upstream
   source (`examples/cli/asr.cpp`, fetched and read this session): no
   `isatty` checks, no progress bars — the CLI prints its whole
   summary (`run:` / `text:` / `segments:` / `realtime:`) only at the
   END; stdout-vs-file and stderr-vs-console change nothing. The
   pipe-vs-bat difference is in HOW output is read, not what the
   child computes.
3. **~2.4x realtime is large-v3-on-Vulkan reality, not a regression.**
   A 14:43 video at the observed pace is a ~6-minute run — normal for
   whisper-large-v3 (the biggest Whisper: 1.5B params, 1.67 GB Q8_0) on
   a Vulkan RTX 3060. And the CLI's own end line prints its throughput
   (`"  realtime:   %.0fx (%.1f ms for %.1f s)"`), which the app never
   parsed or remembered.
4. **The upstream's own speed guidance exists and is specific.**
   `docs/models/whisper.md`: whisper-large-v3-turbo (809M params,
   886 MB Q8_0, WER 2.01% vs large-v3's 1.82% on the upstream's own
   LibriSpeech table) is "the best accuracy/speed tradeoff for most
   multilingual workloads" — a ~4x smaller decoder, no rebuild
   required. And the repo ships `.github/workflows/cuda-windows.yml`:
   CUDA on GeForce is several times faster than Vulkan. Two proven
   faster paths; the log never mentioned either.

## The fix — the speed contract, four additions

1. **`[PARITY]` (computed, per run).** The engine builds the bat's
   canonical argv (`[exe, "-m", model, wav]`) and COMPARES it to the
   command it is about to run: `  [PARITY] byte-identical to your
   transcribe.bat command (same exe, same model, same WAV, no
   app-added flags) — any speed difference vs the bat is NOT the
   command line`. A language hint (`-l en`) is named honestly when
   present ("a language hint costs one decode pass, not minutes").
2. **`[SPEED]` before the wait (the ledger).** New Qt-free stdlib leaf
   `core/transcribe/speed_ledger.py`: a tiny JSON ledger
   (`~/.elixir/transcribe_speed_ledger.json`, atomic write, best-effort
   everywhere — a corrupt/missing ledger is a missing line, never a
   failed run) records the last completed run per model. The next run
   opens with the expectation: `  [SPEED] last run of
   whisper-large-v3-Q8_0.gguf: 2.4x realtime — expect ~6 min for
   14:43 of audio`.
3. **`[SPEED]` at the end (both figures).** The engine parses the
   CLI's own `realtime:` line and logs the wall-clock ratio beside it:
   `  [SPEED] done in 06:12 — 2.4x realtime for 14:43 of audio (the
   CLI's own figure: 2.0x compute-only)` — the wall includes the
   per-run 1.6 GB model reload, the CLI's figure excludes it; printing
   both says where the time went. Both are persisted.
4. **The slow-model hint (data-gated).** A run under 5x realtime on a
   non-turbo whisper earns the upstream's own recommendation: swap to
   whisper-large-v3-turbo (huggingface.co/handy-computer, point the
   Model button at it — no rebuild) or rebuild with the CUDA backend
   (cuda-windows.yml). First slow run: the hint fires at the end,
   where the operator is staring at the finished-but-slow log; later
   runs get it up front from the ledger. Fast runs, turbo models, and
   no-data runs never see it — never a diagnosis without a
   measurement.

The operator's actual `transcribe.bat` is frozen into
`tests/fixtures/transcribe.bat` — the parity pins check the REAL
file's invocation shape, the same ffmpeg conversion, and the same
model path, not a description of them.
