# V0.6.86 — the wizard translation hotfix: the two data-loss bugs (your saved translation models no longer wiped to empty, and the wizard no longer silently turns translation OFF on every run)

> **What this is:** the first step of the approved wizard rework
> (`ELIXIR_WIZARD_REWORK_ROUND_2_PLAN.md`, Phase ① — decision D20:
> "Hotfix both as V0.6.86 immediately, before any rework"). Exactly two
> live bugs are fixed, both in the Process Wizard's translation
> settings, both data-loss bugs. Nothing else changes — no UI rework,
> no behavior redesign; the shell restyle and the Step-1 mode cards
> start with V0.7.0.

## The user reports behind this release

1. *"I configured my Farsi translation models in Settings. After I ran
   a book through the wizard, the Harakat model was gone — the settings
   field was empty."*
2. *"I enabled 'translate outputs after conversion' in the wizard. The
   first book translated fine. The next book didn't translate at all —
   and Settings showed translation disabled again."*

Both reports are one root family: **the wizard wrote over the user's
saved translation settings on every run** — once with garbage (empty
model names), once with a forced "off".

## Bug B1 — the model combos were always empty, and the save wiped your models

**What you saw:** on the wizard's Step 6 (Translation), the "Harakat
model" and "Judge model" dropdowns listed **nothing** — no matter how
many models you had installed in Ollama. If you then started a
conversion, your saved model choices in Settings were overwritten with
an empty value.

**Root cause (the evidence):** the wizard page and the Settings
translation page both called `controller.list_ollama_models()` — a
method that **never existed** on the controller. Both call sites
silently swallowed the error and showed empty dropdowns; the wizard's
save then wrote those empty selections over your saved models.

**The fix (the smallest change the evidence supports):**
- The controller now actually has `list_ollama_models()` — it delegates
  to the app's long-standing, proxy-proof network helper (the same code
  path every other model picker in the app already uses; base URL from
  your configured `llm.ollama_url` setting, 5-second budget so a
  missing Ollama never stalls the page). No new HTTP code.
- A **safety guard** in the wizard's save: an empty model selection can
  **never** overwrite a saved model. If the dropdown comes up empty
  (Ollama down, slow to list), your saved Harakat/Judge models are kept
  untouched, and a log line records that the guard fired. Deliberate
  clearing stays possible from the Settings → Translation page.

## Bug B5 — the wizard force-disabled translation on every run

**What you saw:** translation is a post-conversion step driven by a
saved setting. You enabled it once; every time you ran the wizard, it
silently flipped back to disabled (and the backend, target language,
and which-outputs-to-translate choices reset to defaults).

**Root cause (the evidence):** the wizard's in-memory state defaults
"translation: off", and the wizard never **read** your saved
translation settings when it opened — but it **wrote** them
unconditionally when you pressed Start. So every wizard run stamped
"off" (and the default values) over whatever you had configured.

**The fix:** load-then-save. The wizard now loads your saved
translation settings the moment it opens — enable state, backend,
target language, Harakat/Judge models, and every per-output
translation choice — so Step 6 **shows your actual configuration**,
and pressing Start writes back exactly what you chose (unless you
changed something on the step yourself, which still wins). Fresh
installs with nothing saved still open with translation off.

## What did NOT change

- No wizard UI rework (that starts at V0.7.0 with the stage-chip header
  and the three document-mode cards).
- The translation backend itself, prompts, and the post-conversion
  translation pipeline are untouched — both fixes are in the wiring
  between the wizard UI and the saved settings.
- Quick Convert's "smart defaults" path (which deliberately turns
  translation off for its 3-step runs) is untouched.
- The Settings → Translation page keeps its unconditional save (it
  remains the deliberate-clear path for the Judge model's "use
  summarization model" option).
